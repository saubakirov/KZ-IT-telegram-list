## 1. Objective

Deliver the complete one-source multilingual catalog body for GitHub and the English, Russian,
and Kazakh Pages routes. Phase A makes locale completeness, intent navigation, generator currency,
Markdown portability, and language approval executable while keeping community facts invariant and
leaving site metadata, styling, deployment, and external repository settings to Phase B.

## 2. Scope

### In Scope

- Extend the structured source with the complete EN/RU/KK semantic and UI value set, explicit
  locale review state, and the researched five-intent category-plus-exception definitions.
- Prepare complete English, Russian, and Kazakh candidate wording. Existing Russian descriptions
  are candidates to review, not inherited approval.
- Generate `README.md`, `index.md`, `ru/index.md`, and `kk/index.md` from one locale-aware renderer.
- Make every projection concise and catalog-first, with direct language, type, and intent routes.
- Preserve invariant names, handles, URLs, member counts, verification/archive facts, scope, and
  record cardinality across languages.
- Add explicit stable destinations, portable Markdown escaping, generated target-set checks, and
  regression fixtures for special characters and missing/stale locale or intent data.
- Validate exact GitHub-rendered Markdown behavior through a read-only renderer call bound to the
  generated README bytes or an exact owner-authorized ref; make no external mutation.
- At the very end, obtain a separate Antigravity text-quality assessment, then saubakirov's final
  approval of the complete ready renders and their exact content digest.
- Produce Phase A ONB, evidence, and RF through `/tfw-handoff` after this TS is approved.

### Out of Scope

- `_config.yml`, Jekyll layouts/includes, final HTML head, canonical/`hreflang`, sitemap,
  Dataset/DataDownload markup, social metadata, styling, and deployed viewport work — Phase B.
- GitHub Pages publishing-source changes, repository description/homepage/topics/social preview,
  Search Console, public deployment, recrawl, rank, or AI-inclusion claims.
- Any push, tag, release, or mutation of an external service.
- Telegram liveness/member-count refresh, new community discovery, archive triage, or other live
  catalog-fact changes.
- `llms.txt`, a project-path `robots.txt`, query/keyword pages, client-side search, a web app, CMS,
  or an agent-only content surface.
- Hand-editing any generated catalog file or maintaining language copies independently.
- Treating Antigravity as the formal TFW Reviewer or as authority over the owner's final language verdict.

## 5. Acceptance Criteria

### AC-1: Complete one-source locale and intent contract

The source represents exactly English, Russian, and Kazakh without fallback, preserves all
invariant community facts, and contains the complete localized semantic/UI inventory and the five
researched intent definitions. Before AC-6 these values are complete candidates, not approved copy.

- [ ] Locale keys are exactly `en`, `ru`, and `kk`; every required semantic/UI key is present,
  non-blank, non-placeholder, and explicitly valued even when a technical term is intentionally equal.
- [ ] Names, handles, Telegram URLs, counts, ISO dates, archive facts, category IDs, and record sets
  are locale-invariant and unchanged unless separately evidenced outside this TS.
- [ ] Categories are validated for every entry type that carries one.
- [ ] Intent IDs and order are exactly AI, startups, jobs, events, and engineering; category and
  exceptional-handle references match RES-2 D12 and resolve to existing live entries.
- [ ] Intent membership is derived from source definitions, never localized prose, keywords, or
  duplicated full-entry lists.

Gate: `python scripts/validate_schema.py` plus inspection of the source diff against the pre-phase
catalog facts and the authoritative intent table in RES-2.

Evidence: N/A — source completeness and invariant preservation are deterministic repository checks;
language quality and approval are intentionally deferred to AC-6.

### AC-2: Generate four current, complete projections  [depends: AC-1]

One renderer produces the English GitHub README and the EN/RU/KK Pages bodies. A single check fails
when any generated projection is missing, stale, partial, or inconsistent with source.

- [ ] `README.md`, `index.md`, `ru/index.md`, and `kk/index.md` are generated together and all pass
  the non-mutating currency check.
- [ ] Every projection contains each full live/archive record exactly once with invariant identity,
  facts, and target, plus the selected locale's complete descriptions and labels.
- [ ] Every projection exposes direct links to all three languages in one action and never silently
  substitutes another locale.
- [ ] No generated catalog file contains independently maintained community or translation facts.

Gate: `python scripts/generate_readme.py --check`, schema validation, and generated-set equality
assertions in `python scripts/test_catalog_generation.py`.

Evidence: N/A — generated currency and set parity are fully established by local source/output checks.

### AC-3: Make the ready catalog concise and navigable  [depends: AC-2]

The generated body leads with useful catalog choices and retains only one instance of each distinct
job. Type browsing remains primary; one compact intent map links into the same canonical entries.

- [ ] Each generated body has exactly one primary `h1`, one concise promise, one generated freshness
  signal, language links, type links, and the five intent links before supporting process material.
- [ ] A full live Telegram entry appears before Purpose, non-goals, contribution, workflow, and
  license material; repeated introductory claims and decorative keyword copy are absent.
- [ ] Stable explicit IDs exist for types, non-empty type/category destinations, intents, and
  case-folded handles; localized display text does not own destination identity.
- [ ] Every internal intent/type/language fragment resolves exactly once and no intent duplicates a
  full entry or creates an extra Telegram target.

Gate: Parse all generated Markdown in `scripts/test_catalog_generation.py`; assert ordered structural
roles, unique IDs, resolved fragments, and source-derived intent destinations.

Evidence: N/A — Phase B owns browser viewport/layout evidence; Phase A proves body order and semantic destinations.

### AC-4: Preserve Markdown and GitHub-render target parity  [depends: AC-2]

Special characters, archive structure, explicit IDs, and Telegram links survive both generated
Markdown and GitHub's renderer. The expected pairs derive from source rather than hardcoded totals.

- [ ] Every expected `(visible community name, https://t.me/{handle})` pair exists exactly once in
  generated full entries and in the GitHub-rendered README result.
- [ ] `kzquake`, `mobile_developers_kz`, and `kzqacommunity` are interactive anchors with correct
  visible names and targets, not merely URL substrings.
- [ ] Regression fixtures cover pipe, brackets, emphasis, underscore, backtick, backslash, angle
  bracket, and ampersand behavior.
- [ ] Every internal fragment in GitHub-rendered Markdown resolves to exactly one explicit destination.

Gate: Local regression tests plus a read-only GitHub Markdown-render response for the exact generated
README bytes and recorded SHA-256, or the exact owner-authorized ref when available. Compare parsed
anchor text/URL pairs and internal fragments with source-derived expectations.

Evidence: surface: GitHub rendered Markdown; environment: public GitHub renderer; method: render the
exact candidate bytes or exact ref without mutation and compare source-derived anchor/fragment sets;
artifact: `evidence/EV__phase-a__multilingual_catalog.md`; fallback: none — inability to obtain this
read-only evidence blocks AC-4 and must be reported, never converted to source-only confidence.

### AC-5: Fail safely on drift and invalid inputs  [depends: AC-1]

The validator and regression suite reject the failure modes discovered in research while preserving
the current schema, freshness reporting, and generator-current baseline behavior.

- [ ] Negative fixtures fail for a missing/blank/placeholder locale value, silent fallback, unknown
  locale, invalid category or intent reference, redundant/missing exceptional handle, stale review
  digest, duplicate destination, broken fragment, and lost Telegram anchor.
- [ ] Positive fixtures cover all entry types, archive rows, intentionally unchanged technical terms,
  exact review-digest recomputation, and special-character rendering.
- [ ] Schema validation and generator currency remain non-mutating in check mode and exit non-zero on
  every failure.
- [ ] Existing member-count, date, handle, archive, North Star, and freshness behavior remains covered.

Gate: `python scripts/validate_schema.py`; `python scripts/generate_readme.py --check`;
`python scripts/test_catalog_generation.py`.

Evidence: N/A — deterministic local tests are the authoritative evidence; record command output in EV.

### AC-6: Obtain final independent and owner text-quality verdicts  [depends: AC-3, AC-4, AC-5]

Language review happens only after the complete rendered result is ready. Antigravity supplies an
independent advisory quality pass; saubakirov reviews the final ready renders after that pass and is
the sole authority for Phase A language acceptance.

- [ ] Antigravity reviews all three ready projections for semantic fidelity, natural language,
  Kazakhstan IT/Telegram terminology, concision, tone, and keyword-stuffing risk against the exact
  candidate digest; findings and dispositions are recorded in EV. If unavailable, only an explicit
  owner waiver recorded at this gate may substitute for the advisory pass.
- [ ] saubakirov receives the complete EN/RU/KK renders, Antigravity findings/dispositions, canonical
  payload digest, prior approved reference when one exists, and exact changed-key set.
- [ ] The owner records `APPROVED` or `REVISE` against the exact final digest. `REVISE` returns to
  source edits, regeneration, AC-2–AC-5, and a new final verdict.
- [ ] Any text change after approval invalidates the verdict; no stale approval, machine self-review,
  provider approval, partial-locale approval, or hidden fallback can pass.
- [ ] Phase A RF and formal `/tfw-review` start only after the exact final digest is owner-approved.

Gate: Recompute the canonical NFC/key-sorted payload and changed-key set; match them with the
Antigravity assessment or explicit waiver and the owner's final verdict recorded in EV; rerun every
AC-2–AC-5 command after the last language change.

Evidence: surface: complete rendered EN/RU/KK catalog and review record; environment: final local
candidate plus independent Antigravity assessment and owner chat decision; method: review the exact
digest and changed-key set after all deterministic gates; artifact:
`evidence/EV__phase-a__multilingual_catalog.md`; fallback: Antigravity may be explicitly waived by
saubakirov if unavailable, but owner final approval has no fallback and remains blocking.

## 6. Technical Guidance

- The frozen authority is the Master HL baseline `00a21bb`; research decisions D1–D16 and the exact
  intent audit in Iteration 2 Gather G5 are the implementation reference set.
- Keep community facts under `data/communities.json`; localized values, intent definitions, and
  review state may be structured inside that source as long as the canonical review payload excludes
  invariant facts and its own review metadata.
- Research derives the current common locale manifest from data-backed semantic values plus a shared
  UI registry. The validator should derive required description keys and mutable counts from source,
  not copy the research snapshot totals into code or documentation.
- Canonical review binding is NFC-normalized, key-sorted UTF-8 JSON with SHA-256, an immutable prior
  approved ref/digest when one exists, and a recomputed exact changed-key set. This is guidance for
  reproducibility; equivalent deterministic representation may be used with RF justification.
- Intent definitions are category selectors plus exceptional live handles, with no keyword inference
  or runtime exclusions. Use RES-2 D12 as the baseline semantic fixture.
- Generated destinations should be explicit and locale-invariant: type, type/category, intent, and
  case-folded handle IDs. Empty selected categories emit no dead destination.
- Phase A owns body structure and only the minimal generated front matter needed to declare the three
  routes. Phase B owns layout/head metadata, canonical/alternates, sitemap, Dataset, CSS, public build,
  and bounded browser evidence.
- Prefer extending the existing standard-library scripts and one `unittest` file; do not introduce a
  new runtime or build dependency. The read-only GitHub renderer check may use the project's declared
  `requests` dependency or an equivalent recorded call without external mutation.
- Candidate copy may be machine-assisted, but every candidate remains unapproved until AC-6. Render
  the complete result before asking Antigravity or the owner to assess text quality.
- `README.md`, `index.md`, `ru/index.md`, and `kk/index.md` are generated outputs. Every requested text
  change returns to source and regeneration; direct fixes are prohibited.

## 7. Definition of Failure

- ❌ A generated catalog is hand-edited or any language/community fact is independently duplicated.
- ❌ English, Russian, or Kazakh is missing, partial, placeholder-filled, silently falls back, or is
  accepted without saubakirov's final verdict on the exact ready digest.
- ❌ Antigravity advice is presented as owner approval or formal TFW REVIEW, or its absence is silently ignored.
- ❌ Text changes after owner approval ship without a new digest, checks, and owner verdict.
- ❌ Community identity, liveness, membership, archive, verification, or scope facts change without
  separate evidence and authority.
- ❌ The intent layer uses keywords/localized prose, duplicates full entries, expands the narrow
  catalog, or contains broken/dead destinations.
- ❌ GitHub-rendered Markdown loses an expected Telegram target, visible name, or explicit fragment;
  URL substring presence or generic HTML validity is treated as sufficient evidence.
- ❌ Repeated framing, keyword stuffing, an agent-only surface, `llms.txt`, project-path robots,
  client application, CMS, or search UI enters the phase.
- ❌ Jekyll layout/head/metadata, sitemap/Dataset, styling, deployment, repository settings, Search
  Console, rank, or AI-inclusion work enters Phase A.
- ❌ Any push, tag, release, or external mutation occurs.
- ❌ The phase exceeds a scope budget without returning to `/tfw-plan`.

Any failure must be corrected before RF. A blocked read-only renderer or final owner review is
reported as a specific blocker; it is never converted into a partial approval.

## 8. Phase Risks

| Risk | Mitigation |
|------|------------|
| Final review causes wide wording churn | Freeze structure first; review complete renders together; regenerate and rerun all checks after changes |
| Kazakh candidate is fluent but semantically inaccurate | Antigravity advisory plus owner final authority; explicit invariants and no fallback |
| Existing Russian text is assumed approved | Treat every RU value as candidate and include it in the same final digest/review gate |
| Broad Engineering intent misleads users | Preserve the researched category/exception semantics and exclusions; derive membership from source |
| Four outputs drift | One renderer and currency command fail the whole set |
| GitHub rendering differs from source assumptions | Compare parsed anchor pairs/fragments on exact rendered candidate bytes |
| Generated content becomes bloated | AC-3 enforces one job per retained first-screen block and catalog-before-process ordering |
| Phase B leaks into Phase A | AC-7 and the eight-path file budget reject metadata/layout/deployment changes |
